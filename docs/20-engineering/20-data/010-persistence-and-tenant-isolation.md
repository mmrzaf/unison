# Persistence and Tenant isolation

PostgreSQL is the authoritative structured data store. Tenant ownership, purpose, identifiers, timestamps, quantities, canonical codes, immutability, and deletion semantics are explicit in schema and query boundaries.

## The authoritative structured data store

Waiotech must use PostgreSQL as the source of durable structured truth.

PostgreSQL is the authoritative store for structured Waiotech business state, evidence metadata, audit, revisions, assignments, Command Receipts, outbox records, process records, integration obligations, and reconciliation.

## Keep caches and queues non-authoritative

Waiotech must keep caches and queues non-authoritative.

Redis and process-local caches may hold delivery, coordination, rate-limit, and rebuildable read data. Cache loss or Redis loss must not erase accepted commands, lifecycle, process obligations, or evidence.

## Make persistence ownership correspond to module ownership

Waiotech must make persistence ownership correspond to module ownership.

Each product module owns its tables, constraints, indexes, migrations, and repository mappings. Shared platform tables have an explicit platform owner. Table location does not transfer product ownership.

## Make operational and learning purpose explicit and immutable in authoritative persistence

Waiotech must make operational and learning purpose explicit and immutable in authoritative persistence.

Tenant purpose uses a product-owned constrained code with exactly `operational` and `learning`. It is required, immutable after Tenant creation, included in Tenant-context loading, and covered by database and architecture tests.

## Never infer learning isolation from naming convention

Waiotech must never infer learning isolation from naming convention.

Side-effect fencing, reporting exclusion, reset authority, and content visibility use the authoritative purpose field.

## Enforce purpose isolation in every cross-Tenant operational query

Waiotech must enforce purpose isolation in every cross-Tenant operational query.

Ordinary Tenant isolation through `tenant_id` always applies. Platform-wide operational queries, report selection, integration scans, billing scans, support queues, and delivery workers also apply the required purpose predicate or use an owned query contract that excludes learning Tenants.

## Represent Tenant scope explicitly in authoritative persistence

Waiotech must represent Tenant scope explicitly in authoritative persistence.

Every Tenant-owned row contains a non-null Tenant identifier or belongs through an immutable parent relationship whose Tenant is enforced by database constraints. Ordinary cross-Tenant relationships are prohibited.

## A Tenant-aware foreign key

Waiotech must use database constraints to prevent cross-Tenant relationships.

A Tenant-aware foreign key verifies both referenced identity and Tenant equality, ordinarily through a composite key such as `(tenant_id, referenced_id)`. Application checks supplement but do not replace applicable database constraints.

## Require explicit Tenant identity wherever it improves isolation and verification

Waiotech must require explicit Tenant identity wherever it improves isolation and verification.

Every independently queried or related Tenant-owned table should contain `tenant_id`. A tightly owned child may inherit Tenant through a constrained parent when direct storage would add no verification value. The choice must not weaken query safety or foreign-key enforcement.

## Never use an absent Tenant as an implicit superuser or platform path

Waiotech must never use an absent Tenant as an implicit superuser or platform path.

Platform-scoped records have an explicit platform scope and cannot be confused with a missing Tenant. Nullable Tenant identifiers are prohibited unless a typed scope discriminator and constraints make the distinction unambiguous.

## Separate immutable technical identity from human operational codes

Waiotech must separate immutable technical identity from human operational codes.

Durable entities use opaque UUID identifiers generated by trusted application or database mechanisms. Human-facing operational codes are separate, Tenant-scoped where applicable, and never substitute for technical identity.

## Make business codes stable and interpretable

Waiotech must make business codes stable and interpretable.

A code contract defines scope, normalization, case sensitivity, uniqueness, immutability, retirement, and correction. Code reuse after historical use is prohibited unless Product Authority explicitly defines equivalent identity.

For optional Plant Model codes, persistence preserves the entered display form and also stores or derives a deterministic comparison key by trimming surrounding whitespace, applying Unicode NFKC normalization, and Unicode case folding. Empty values and control characters are rejected. Uniqueness is enforced on `(tenant_id, plant_entity_category, normalized_code)` for active and historically reserved code ownership as required by Product Authority.

## Preserve the distinction between instants and local calendar meaning

Waiotech must preserve the distinction between instants and local calendar meaning.

Recorded instants use timezone-aware PostgreSQL timestamps representing unambiguous instants. Local dates, local times, and Tenant timezone identifiers use separate typed fields when they are product facts. Naive timestamps are prohibited for recorded instants.

## Preserve decimal meaning across persistence and APIs

Waiotech must preserve decimal meaning across persistence and APIs.

Quantities, rates, costs, and money use exact PostgreSQL numeric types with contract-defined precision and scale. Floating-point storage is prohibited for authoritative exact values.

## Keep persistence language-independent and code-stable

Waiotech must keep persistence language-independent and code-stable.

Lifecycle, catalogue, action, event, and reason identities use stable machine codes. Display labels are not stored as identity. Database constraints or reference tables enforce permitted values where compatible with retirement and migration rules.

## Preserve orthogonal Plant Model identity in persistence

Waiotech must preserve Functional Location, Asset, Process Unit, Process Stream, and Measurement Point as distinct persisted identities.

Persistence must not encode them as one universal entity table whose discriminator becomes the real source of domain meaning. Shared technical infrastructure is permitted, but owning tables, constraints, repositories, and relationships must preserve the explicit Product Authority concepts.

Functional Location containment, Asset physical composition, Asset installation, Process Unit containment, Process Stream direction, Functional-Location-to-Process-Unit service relationships, and Measurement Point subject relationships each require constraints appropriate to their own semantics.

Where Product Authority requires effective history, persistence stores non-overlapping effective periods instead of overwriting the prior relationship. Asset physical composition has at most one effective parent per Asset and must remain acyclic. A composed child Asset cannot carry a competing direct Functional Location installation; its installed context is resolved through the effective containing-Asset chain. Measurement Point subject and quantity changes that would alter semantic identity are represented by retirement and new identity rather than row mutation.

## Preserve Asset installation history rather than overwriting current placement

Asset installation is effective-dated authoritative history.

Persistence prevents overlapping active installations for one Asset and preserves removal and replacement history. A current-installation projection may be derived, but it cannot replace the historical relationship as authority.


## Persist Process Routines and Rounds without duplicating Process evidence

Published Process Routine Revisions are immutable revision records. Scheduled Process Round occurrence identity is protected by a deterministic uniqueness constraint over Routine and nominal occurrence identity.

A Process Round stores execution state and references accepted Process Readings and Operational Observations by canonical identity. It must not copy those values into mutable Round-entry columns that could diverge from Process evidence.

## Persist Process Readings as append-only operational evidence

Accepted Process Readings are append-oriented records with explicit Measurement Point, effective time, recorded time, Actor, provenance, quality, reported value and unit, normalized canonical representation where applicable, and source identity.

Machine-submitted source identity and idempotency must permit duplicate-safe retry without creating duplicate accepted Readings. Correction uses additive relationships rather than in-place rewriting.

## Protect historical meaning through immutable persistence patterns

Waiotech must protect historical meaning through immutable persistence patterns.

Published revisions, audit, posted Inventory Movements, accepted Decisions, completed artifacts, event envelopes, and other immutable evidence have no ordinary update or delete path. Constraints, repository APIs, and architecture tests enforce append-oriented correction.
