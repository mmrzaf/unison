# Catalogues and generated reference data

Product-owned catalogues use stable governed codes, canonical source definitions, localization, retirement, generation, API exposure, and migration rules. Tenant master data remains separate and cannot create executable product behavior.

## A catalogue

Waiotech must treat catalogue values as product contracts rather than editable labels.

A catalogue is a governed set of stable coded values used to classify, constrain, authorize, or interpret product behavior. It defines code, meaning, owner, applicability, lifecycle, relationships, and presentation metadata.

## A taxonomy

Waiotech must use taxonomy only when structure is part of the contract.

A taxonomy is a governed classification structure whose values have hierarchical or semantic relationships. Not every catalogue is hierarchical, and not every hierarchy is product-fixed.

## Do not infer catalogue ownership from use in a dropdown or table

Waiotech must not infer catalogue ownership from use in a dropdown or table.

Tenant master data represents Tenant-owned operational identities such as Item, Item Category, Stock Location, Team, or another Product Authority concept. Product-owned catalogue values have one Waiotech-defined meaning across Tenants.

## Declare governance explicitly in Product Authority

Declare governance explicitly in Product Authority.

Each governed value set is classified as:

1. product-fixed closed catalogue;
2. product-managed governed extension point;
3. Tenant-governed catalogue;
4. Tenant master data;
5. derived registry or reference.

## Derive governance from Product Authority only

Waiotech must derive governance from Product Authority only.

A database table, active flag, CRUD component, or localization support does not grant Tenant authority. Source-code storage does not independently prove product ownership.

## Keep Tenant purpose closed, stable, and product-owned

Waiotech must keep Tenant purpose closed, stable, and product-owned.

Tenant purpose is a product-fixed closed catalogue owned by the Tenant domain with exactly `operational` and `learning`. Tenants cannot add, rename, reinterpret, or retire purpose codes. Persistence, APIs, generated clients, reporting exclusions, side-effect fences, and tests derive from the same canonical definition.

## Use one product-wide Maintenance discipline catalogue

Waiotech must use one product-wide Maintenance discipline catalogue.

One Waiotech catalogue defines every Maintenance discipline code and meaning. A Tenant may declare applicability to canonical codes but cannot create, rename, reinterpret, or retire disciplines.

## Separate Tenant applicability from catalogue ownership

Waiotech must separate Tenant applicability from catalogue ownership.

A separate Tenant-to-canonical-code relationship controls ordinary selection. It does not create a Tenant-specific discipline or change historical records when applicability ends.

## Keep catalogue meaning module-owned

Waiotech must keep catalogue meaning module-owned.

The product module owning the meaning owns the canonical definition. A shared generator validates and combines definitions but does not become business owner.

## Share generation infrastructure without creating an unowned taxonomy domain

Share generation infrastructure without creating an unowned taxonomy domain.

Shared tooling may load, validate, localize, and generate catalogue representations. It cannot centralize unrelated product meanings into a universal catalogue service.

## The canonical source format

Waiotech must maintain one reviewable source of truth for every product-owned catalogue.

A catalogue uses one source-controlled typed definition owned by its module. The source declares catalogue identity, code, canonical meaning, lifecycle, localization key, relationships, dependencies, and generation requirements. The wastewater taxonomy is owned by `server/reference-data/taxonomy/catalogue.json` and validated and generated by `server/scripts/generate_taxonomy.py`.

Generated representations include Server validation metadata, read-only PostgreSQL reference rows seeded by the canonical migration, Dashboard TypeScript, Android Kotlin where the Android contract consumes the canonical definition, localization coverage, and contract tests. Generated database rows have no runtime CRUD authority and must match the governed source digest.

Operational-code metadata is explicit. A taxonomy encoding token does not automatically become an entity-code token. Categories declare whether and how a value contributes to a module-owned operational-code policy. The Server allocates entity codes transactionally; browsers only display a non-reserving pattern.

## Use language-independent stable machine identities

Waiotech must use language-independent stable machine identities.

Ordinary catalogue codes use stable lowercase ASCII `snake_case` within their owning catalogue. Permission and action codes use their module-qualified dotted standards. Codes do not contain labels, Tenant prefixes, or database sequence meaning.

## Protect historical records, events, reports, exports, and integrations from code drift

Waiotech must protect historical records, events, reports, exports, and integrations from code drift.

A used code is permanent identity. A label may change when meaning remains unchanged. A new meaning requires a new code. A retired code remains reserved and interpretable.

## Avoid a global catalogue version that obscures code-level compatibility

Avoid a global catalogue version that obscures code-level compatibility.

Stable codes and preserved definitions provide historical interpretation. Generated manifests may carry source commit, digest, generator identity, and schema version as provenance.

## Separate identity and meaning from presentation language

Waiotech must separate identity and meaning from presentation language.

Localization uses stable keys derived from catalogue and code. APIs and persistence use canonical code. Missing translations use the governed fallback locale and fail verification when coverage is mandatory.

## Treat addition as a governed product-contract change

Waiotech must treat addition as a governed product-contract change.

Addition requires Product Authority support, module-owned source change, stable code, behavior implementation where applicable, localization, generated output, persistence support, contract-version review, migrations, and tests.

## Apply retirement prospectively and preserve history

Waiotech must apply retirement prospectively and preserve history.

Retirement prevents unsupported new use while preserving historical reads, audit, events, reports, exports, and integration interpretation. Retirement never deletes or reassigns the code.

## Do not silently reinterpret historical codes

Waiotech must not silently reinterpret historical codes.

Only when Product Authority declares semantic equivalence for the affected records. Otherwise, conversion requires an explicit correction or migration preserving original and replacement evidence.

## Surface unknown codes as integrity defects

Surface unknown codes as integrity defects.

Unknown input is rejected. Unknown persisted product-owned code is a data-integrity non-conformance and is not coerced to `other`, empty, or a similar value.

## Prohibit generic escape values without a domain contract

Waiotech must prohibit generic escape values without a domain contract.

`Other` exists only when Product Authority defines its meaning, supporting text, reporting effect, and behavioral limits.

## Keep reasons tied to the action whose meaning they explain

Waiotech must keep reasons tied to the action whose meaning they explain.

Each action family owns its reason-code catalogue. A generic global reason table is prohibited. Each family declares ownership, extension authority, supporting text, lifecycle, reporting meaning, and integration behavior.

## Keep Permission meaning module-owned and assembly centralized

Waiotech must keep Permission meaning module-owned and assembly centralized.

Product modules define protected Permissions. IAM assembles a generated catalogue with stable code, owner, description, dependencies, protected actions, sensitivity, and lifecycle. Tenants cannot create Permission codes.

## Separate control definition from Tenant-configured value

Waiotech must separate control definition from Tenant-configured value.

Tenant Control types are product-owned typed definitions declaring code, value type, constraints, dependencies, publication validation, impact behavior, and sensitivity. Tenants configure values through Tenant Control Policy but cannot create control types.

## Generate every repeated representation from canonical definitions

Waiotech must generate every repeated representation from canonical definitions.

Generation may produce backend types, validation metadata, database reference synchronization, OpenAPI values, TypeScript and Kotlin values, localization manifests, read-only catalogue responses, documentation, version manifests, and test fixtures.

## Generate only representations required by the contract

Waiotech must generate only representations required by the contract.

Output depends on use. A small closed value may generate types. A rich Permission catalogue may generate metadata and queries. Tenant-owned master data uses ordinary persistence and APIs.

## Use database tables as derived persistence representations

Waiotech may use database tables as derived persistence representations when relational constraints or rich metadata require them. Rows remain synchronized from canonical source and have no Tenant CRUD authority.

## Prohibit direct editing of product-owned reference rows

Waiotech must prohibit direct editing of product-owned reference rows.

Changes occur through canonical source, approved migration or synchronization, verified generation, and release.

## Keep API identity language-independent and governance-safe

Waiotech must keep API identity language-independent and governance-safe.

Commands submit canonical codes. Read responses may add localization key, label, description, owner, group, and active or retired condition. Product-fixed catalogue endpoints are read-only.

## Model Tenant-governed values as real domain concepts

Waiotech must model Tenant-governed values as real domain concepts.

Each is an explicit module-owned entity and API contract defining Tenant identity, code scope, lifecycle, hierarchy, Permission, history, import, export, and retirement. A universal `custom_value` table is prohibited.

## Prevent ungoverned behavior from attaching to configurable values

Waiotech must prevent ungoverned behavior from attaching to configurable values.

Only when Product Authority explicitly defines that behavior. A label or category cannot grant Permission, change lifecycle, alter Plan resolution, post Inventory, or invoke arbitrary automation.

## Make catalogue drift release-blocking

Waiotech must make catalogue drift release-blocking.

Continuous integration verifies source validity, unique codes, no code removal or reassignment, dependency resolution, localization, generated parity, OpenAPI and client parity, database reference parity, and absence of forbidden Tenant CRUD.

## Use evidence-backed mappings and normalize aliases before canonical storage

Waiotech must use evidence-backed mappings and normalize aliases before canonical storage.

Each value is classified as exact match, approved alias, distinct canonical code, Tenant master data, or unsupported ambiguity. Migration preserves original value, mapping, reason, provenance, affected records, and unresolved cases.
